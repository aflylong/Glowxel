# ESP32 Glowxel PixelBoard 开发环境说明

更新日期：2026-04-07

说明：本文里的固件实现仍属于 `Glowxel` 仓库；对外设备正式名称统一为 `Glowxel PixelBoard`。

## 1. 环境配置

### 已安装工具

- Python 3
- PlatformIO

推荐命令：

```bash
cd esp32-firmware
.\pio.cmd run
.\pio.cmd run --target upload ### 烧录
.\pio.cmd device monitor ### 串口打印
```

Windows PowerShell 里执行当前目录下的脚本必须带 `.\`。如果写成 `pio.cmd run`，PowerShell 会优先从 PATH 里找命令，不会自动执行当前目录的 `pio.cmd`。

### 本地烧录和网页烧录的区别

本地开发时，通常只需要：

```bash
cd esp32-firmware
.\pio.cmd run -t upload
```

PlatformIO 会自动处理 bootloader、分区表、应用程序等烧录步骤。开发阶段不需要手动复制 bin 文件。

官网 `/device-flash` 页面使用的是 ESP Web Tools + Web Serial。浏览器不能像 PlatformIO 一样自动理解整个工程，所以必须提供一份 manifest，并把每个 bin 按固定地址交给浏览器烧录。

当前网页烧录需要的文件见：

- [../website/public/firmware/esp32/README.md](../website/public/firmware/esp32/README.md)

对应关系：

| 文件 | 地址 | 说明 |
| --- | ---: | --- |
| `bootloader.bin` | `0x1000` | 二级启动程序 |
| `partitions.bin` | `0x8000` | 分区表，来自 `partitions.csv` |
| `boot_app0.bin` | `0xE000` | Arduino ESP32 启动辅助数据 |
| `firmware.bin` | `0x10000` | 主程序 |
| `littlefs.bin` | `0x3F0000` | LittleFS 数据分区镜像 |

生成网页烧录发布文件时，按下面三步执行：

```bash
cd esp32-firmware
.\pio.cmd run
.\pio.cmd run -t buildfs
.\scripts\prepare-web-flash-release.ps1
```

前两条命令只负责生成固件构建产物，不会自动放到网站目录：

```text
esp32-firmware/.pio/build/esp32dev/bootloader.bin
esp32-firmware/.pio/build/esp32dev/partitions.bin
esp32-firmware/.pio/build/esp32dev/firmware.bin
esp32-firmware/.pio/build/esp32dev/littlefs.bin
```

第三条 `prepare-web-flash-release.ps1` 才负责把网页烧录需要的 5 个文件复制到官网静态目录：

```text
website/public/firmware/esp32/bootloader.bin
website/public/firmware/esp32/partitions.bin
website/public/firmware/esp32/boot_app0.bin
website/public/firmware/esp32/firmware.bin
website/public/firmware/esp32/littlefs.bin
```

`boot_app0.bin` 来自 PlatformIO 的 Arduino ESP32 framework package，脚本会从本机 PlatformIO packages 目录读取。整理完成后，这些文件会通过官网静态路径 `/firmware/esp32/` 提供给 `/device-flash` 页面使用。

不要把网页烧录和设备 WebSocket 控制混在一起：网页烧录走 USB 串口，WebSocket 是设备已经运行并连上网络后的控制通道。

### 常见问题

- 端口被占用：Windows 下在设备管理器查看 COM 端口，或用 `mode` 命令列出串口
- 无法识别串口：检查数据线和驱动（CH340/CP2102），确认设备管理器中出现对应 COM 口
- 编译异常：优先重新执行 `pio.cmd run`，不要手改 `.pio/` 中间产物
- 如果直接用全局 `platformio` 命令看到 `RequestsDependencyWarning`，优先改用项目内的 `pio.cmd`；这是 Python 依赖告警，不是固件编译错误

## 5. 资源优化与内存边界

以后做板载主题资源优化时，**不要只看资源文件大小**，一定要同时看：

- Flash / PROGMEM 是否下降
- `.dram0.bss` 运行时常驻内存是否上升

这两者不是一回事。

典型风险：

- 为了省 Flash，引入了新的 `static` 大数组
- 把稀疏像素先展开成整图 RGB888 缓冲
- 为了缩放、差分重建、混合，新增了常驻 LUT / 中间 buffer

这些都可能导致：

```text
.dram0.bss will not fit in region dram0_0_seg
region `dram0_0_seg' overflowed
```

这类信息不是 warning，而是 **链接失败**，固件不会生成。

### 每次资源优化后的必做检查

```bash
cd esp32-firmware
.\pio.cmd run
```

重点看：

- 是否成功链接
- RAM 占用是否明显上升
- Flash 占用是否在预算内

建议边界：

- RAM 尽量控制在 `50%` 以下
- Flash 尽量控制在 `70%` 以下

如果优化让 Flash 变小了，但 DRAM 明显上升甚至导致链接失败，这次优化就不能直接接受，必须继续收缩运行时缓存。

### 本次 KOF97 / Adventure Island 踩坑记录

- 初始状态：`.dram0.bss` 超出 `11776 bytes`
- 第一轮收缩后：仍超 `512 bytes`
- 最终修复后：成功编译
- 结果：`RAM 124192 / 327680 (37.9%)`，`Flash 2337129 / 4063232 (57.5%)`

结论：

> 板载资源优化必须同时守住 Flash 和 DRAM 两条边界，不能只盯一种。
