# ESP32 Glowxel PixelBoard 开发环境说明

更新日期：2026-04-07

说明：本文里的固件实现仍属于 `Glowxel` 仓库；对外设备正式名称统一为 `Glowxel PixelBoard`。

## 1. 环境配置

### 已安装工具

- Python 3
- PlatformIO

推荐命令：

```bash
cd esp32-firmware
pio.cmd run
pio.cmd run --target upload ### 烧录
pio.cmd device monitor ### 串口打印
```

### 常见问题

- 端口被占用：Windows 下在设备管理器查看 COM 端口，或用 `mode` 命令列出串口
- 无法识别串口：检查数据线和驱动（CH340/CP2102），确认设备管理器中出现对应 COM 口
- 编译异常：优先重新执行 `pio.cmd run`，不要手改 `.pio/` 中间产物
- 如果直接用全局 `platformio` 命令看到 `RequestsDependencyWarning`，优先改用项目内的 `pio.cmd`；这是 Python 依赖告警，不是固件编译错误

## 5. 资源优化与内存边界

以后做板载主题资源优化时，**不要只看资源文件大小**，一定要同时看：

- Flash / PROGMEM 是否下降
- `.dram0.bss` 运行时常驻内存是否上升

这两者不是一回事。

典型风险：

- 为了省 Flash，引入了新的 `static` 大数组
- 把稀疏像素先展开成整图 RGB888 缓冲
- 为了缩放、差分重建、混合，新增了常驻 LUT / 中间 buffer

这些都可能导致：

```text
.dram0.bss will not fit in region dram0_0_seg
region `dram0_0_seg' overflowed
```

这类信息不是 warning，而是 **链接失败**，固件不会生成。

### 每次资源优化后的必做检查

```bash
cd esp32-firmware
pio.cmd run
```

重点看：

- 是否成功链接
- RAM 占用是否明显上升
- Flash 占用是否在预算内

建议边界：

- RAM 尽量控制在 `50%` 以下
- Flash 尽量控制在 `70%` 以下

如果优化让 Flash 变小了，但 DRAM 明显上升甚至导致链接失败，这次优化就不能直接接受，必须继续收缩运行时缓存。

### 本次 KOF97 / Adventure Island 踩坑记录

- 初始状态：`.dram0.bss` 超出 `11776 bytes`
- 第一轮收缩后：仍超 `512 bytes`
- 最终修复后：成功编译
- 结果：`RAM 124192 / 327680 (37.9%)`，`Flash 2337129 / 4063232 (57.5%)`

结论：

> 板载资源优化必须同时守住 Flash 和 DRAM 两条边界，不能只盯一种。
